# Development and publication

Only reusable source, scripts, synthetic tests, pinned dependency identifiers and public-facing documentation belong in Git. The root ignore rules intentionally allowlist these files. Local research/history, external fixtures, captures, logs, game-derived output and builds are excluded. Source-level diagnostic support is part of the runtime; recorded diagnostics are not part of the repository.

Before pushing, run `python tools/check-source-package.py --tracked` and inspect `git diff --cached --stat`. This checks the selected publication files for binary data, game/build outputs, machine-specific paths and common credential patterns. It is an additional guard, not proof that arbitrary future files are appropriate to publish. Never force-add game files around the ignore rules.

## Synthetic tests

After dependency setup, from PowerShell:

```powershell
. .\tools\dev-env.ps1
cmake -S tools/tests -B 'D:\SFIII-checks' -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++ "-DSATURN_RUNTIME=$PWD/.local/saturn-recomp/runtime"
cmake --build 'D:\SFIII-checks' --target dsp_regression core_regression bup_regression machine_regression background_regression audio_buffer game_speed
```

Run each executable from the checks directory. Also build and run `hd_assets` and `hd_pack_index`, passing a new external fixture directory to each. GPU/UI synthetic targets are available in the generated game's build; captured video inputs are optional external data and must never be committed. A test without its required fixture is unavailable validation, not a pass. Public tests use invented data; local captured routes are not distributed.

Also run `game_speed` for 1×/2×/3× deadlines, stalls and restored clocks. The SDL `replay_ui_selftest` exercises speed-button/F6/menu changes, queue clearing, scaled audio priming and pause rebasing with synthetic data. `validate-game-speed.py` complements headless transition checks with a windowed, audio-enabled replay comparison at all three rates. Its report separates requested and achieved speed from identical native pixels/video memory, virtual PCM and backup contents. The route manifest, exact initial backups, clock and inputs must be external. Fast-forward is whole-game host pacing, not a modification to battle logic; pitch follows the audio playback ratio.

The current optional-artwork preview hides the earlier AA and Ray shadows controls. Their retained experimental implementation and regression tests are described here for developers. Light AA uses an optional second GPU pass in the geometry shader. Tests cover diagonal edges, protected sprite/native layers, odd dimensions, repeated-frame caching and exact Off restoration; optional external captures also verify protected samples and compare timing. `validate-game-speed.py --aa` checks a real route with filtering enabled. Vulkan and Direct3D 12 were tested locally on Windows. Metal conversion now explicitly preserves uniform-first SDL buffer bindings and rejects incorrect mappings; this is conversion validation, not Mac GPU execution or Linux/macOS gameplay validation.

The experimental Ray shadows option shares that second GPU pass. A bounded screen-space ray checks visible owner IDs and large projected geometry receivers, then darkens eligible pixels near smaller foreground occluders. It is not hardware ray tracing and cannot reconstruct hidden world geometry. Shader tests cover 2×, 4× and 5× output, protected sprites, AA combination, cache invalidation and exact Off restoration. An external captured Scenario 2 frame was compared on Windows Vulkan at 5×; broader scene coverage and other GPU backends remain unvalidated. Keep this effect opt-in and preserve original rendering as the default.

The separate AI graphics trial uses external exact-match replacement packs for opaque, GPU-eligible distorted-sprite textures captured from a Scenario 2 church interior, battle and Airo village. AnimeVideo v3, x4plus anime and x4plus general packs are generated offline from the player's local disc data. The runtime projects the selected pack with the shared SDL GPU device after native geometry and before menus; unmatched art stays original. This does not run an inference model during gameplay or imply full-game texture coverage. `render_dump_gpu` compares GPU and CPU overlays, including effects/occlusion and flips, while `replay_ui_selftest` checks all menu modes. Keep raw captures, pack contents and test output outside the source tree.

`tools/offline-assets/install.ps1` assembles a separate Windows desktop builder from explicit local dependency paths: a Python/Pillow/Tk runtime, SF3Tools checkout, saturn-recomp checkout, Real-ESRGAN Vulkan directory and chdman. It publishes the C# extraction adapter with external build/intermediate paths and copies the runtime into the external installation; end users do not compile or depend on Codex being installed/running. The adapter reads disc-derived files without saving them, normalizes Saturn five-bit channels with `<< 3` for native texture matching, and records unsupported/partial decodes. Do not redistribute upstream resources or generated artwork as project source.

`tools/offline-assets/package.py` builds the optional public Windows download from a redistributable Python/Tk/Pillow runtime and our source. Its first-run `bootstrap.py` downloads checksum-pinned tools and SF3Tools directly upstream, then compiles the adapter locally. SF3Tools has no redistribution license in the pinned tree: its binaries, resources and prepared setup directories must not be shipped. The network-free `install.ps1` path above is a maintainer installation option using already supplied local dependencies.

The worker uses per-file decoder/source hashes, full asset identities, model/weight signatures, short checked cache prefixes, atomic receipts, a single-worker output lock, and stop-aware child-process handling. GPU atlas pages amortize model startup while padding individual materials and restoring the original alpha mask afterward. World packs use the existing SF3HDASSET1 format; the character extension below adds eligible CHR/CHP sprites. Background-plane replacement remains unsupported. Tests cover periodic context, transparent RGB filling, exact alpha, resume, corrupt cache rejection, black-output rejection, long receipt paths, traversal rejection and stopping an active child. Missing dependencies must be reported as skipped/unavailable, not passing coverage.

GPU batches allow fifteen minutes by default (`gpu_timeout_seconds`, minimum five minutes); changing this limit retains the model cache. Start / Resume retries missing results, while rejected black results remain gaps. `tools/offline-assets/select_packs.py` writes an external selection from one revision's three model manifests; the main launcher consumes a revision-validated selection through `desktop/ai_packs.py`. That module canonicalizes supported profile IDs, pins manifest bytes and preserves previous selections. Copied source-build helpers must retain the same behavior. Pack attachment does not alter ordinary saves.

Overlay diagnostics compare alpha and the composed RGB over both black and white at the existing 2/255 tolerance. Straight-alpha RGB at zero opacity has no displayed meaning, so raw RGB alone is not a valid translucent-edge comparison. Synthetic checks retain opaque errors, alpha errors, semitransparent colour errors and the alpha-zero/one interpolation boundary. This diagnostic rule does not change runtime rendering.

The character trial combines world packs with exact-source CHR/CHP sprite frames, with a `character` descriptor tag after the UV range. Legacy/world descriptors retain distorted-sprite-only matching; character descriptors also permit normal and scaled sprites. It does not add palette-mode decoding or enhance every portrait/embedded menu image. `character_packs.py` verifies full scaled alpha masks and hashes, creates a separate immutable combined pack, and hardlinks payloads when available. Shared world/character materials receive a new descriptor without changing the source world pack.

`HdAssets` loads replacement pixels on demand with a 256 MiB soft cache per style, pinning the current frame's matches. `HdGpu` uploads only visible materials and reuses the resident buffer when that set is unchanged. Streaming diagnostics cover empty/populated transitions, buffer growth, normal/scaled character gating, unsupported commands and exact guest-video immutability. CPU cache tests exercise animation changes, eviction/reload and command changes without a geometry-counter change. Real character coverage remains limited to the captured Scenario 2 scenes and tested continuations; packaging all extracted frames is separate from campaign coverage.

Published local packs are immutable. `index_packs.py` writes a `materials.sf3idx` startup index containing descriptors, relative replacement paths and complete original RGBA. The native loader opens this single file instead of scanning thousands of materials; replacement pixels still load on demand. Exact manifest bytes invalidate stale indexes; bounded parsing and FNV64 checks detect corruption, with ordinary directory loading as fallback. FNV is not package authentication. When editing a pack, update its manifest or generate a new immutable pack. Both builder packaging paths generate indexes automatically. Index creation and all game-derived index bytes stay outside the source repository.

The native `hd_pack_index` regression checks indexed/directory rendered equality, lazy loading, corruption/truncation/version/UV/dimension/path rejection, manifest changes and missing replacement fallback. `hd-pack-probe.cpp` measures pack loading without modifying it. Startup logs distinguish cached indexing from directory scans and record per-style loading time. These timings cover artwork initialization, not the whole launcher/disc hashing sequence.

`archive_packs.py` measures logical size and hardlink-deduplicated content separately, performs deterministic stratified lossless compression samples, and can make a full ZIP with decompressed SHA-256 verification. Regenerable startup indexes are excluded; rebuild them after restoring a pack. Current gameplay reads extracted RGBA files, not ZIP or PNG replacements directly. Sample-based compression projections must remain labelled estimates. Keep local archives and reports outside Git; publish the reusable builder and model recipes instead of original or processed game artwork unless redistribution rights have been resolved. GitHub release attachments have a [per-file limit below 2 GiB](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

Design references: [Snap64 Recomp v1.0.8](https://github.com/JackandBeans/Snap64Recomp/releases/tag/v1.0.8) documents fast-forward through accelerated clocks, reduced presentation work and faster/higher-pitched audio. This is its maintainer's documented behavior; that project was not built or tested here. Our audio path uses SDL's [stream frequency ratio](https://wiki.libsdl.org/SDL3/SDL_SetAudioStreamFrequencyRatio), which changes consumption speed and pitch. The machine still generates its original PCM. At 2×/3× we execute every machine field but compose/present every second/third host picture, preserving the selected resolution while limiting CPU/GPU presentation overhead. Input polling, VDP1 execution, interrupts and sound continue on skipped pictures; requested diagnostic screenshots and video recording can force extra composition. This does not certify complete battles, every scene or campaign-wide determinism.

Before promoting runtime changes into an existing playing installation, also replay the exact available transition fixtures using preserved initial internal/cartridge backups, clock, settings and input. Compare native frame/video hashes and inspect changed frames. Preserve the previous runnable build and checkpoints. Never use historical validation saves as live progress. Local maintainer transition tooling and fixtures may be kept separately; the public source does not reproduce private route fixtures by itself.

`validate-native-states.py` also accepts an external route with `state_in` to begin directly at a native snapshot. Audio suffix comparisons account for the snapshot's existing sample count. Exercise repeated snapshots before and after overlay transitions, as well as uninterrupted startup routes; a successful state load alone does not validate the next requested module. Fixtures must match the exact executable/disc identity. Keep old states intact when changing builds; this tool does not automatically migrate them.

Some BOOT drawing-command wrappers save PR on the SH-2 stack before calling a shared queue guard. When the guard rejects a command, it restores that saved PR and returns directly to the wrapper's caller. The three verified call sites in each supported revision are listed as `stack_return_calls` in its BOOT profile. The generated code accepts this return only when the callee popped exactly one saved word and returned to that word's address; every other unexpected return remains an error. Synthetic generated-code tests compare the normal and rejection paths against the SH-2 reference interpreter, including wrong stack and target cases. The external transition manifest also includes the recorded Scenario 2 Waltz rejection path. Keep this exception tied to disassembly evidence for each revision rather than applying it to all calls.

## All-revision module checks

Run `python tools/validate-modules.py --manifest <external-manifest.json> --out <new-external-directory> --jobs 2` to audit, emit, compile and boot every registered revision using local inventories and discs. The external manifest supplies `cmake`, optional `tool_paths`, `cmake_args`, `sdl_dll`, `build_jobs`, and a `revisions` list. Each revision specifies a safe unique `id`, source `profile`, external `inventory` (with `extract` and `manifest.json`) and `cue`. An optional `reuse` object supplies existing `audit`, `generated` and `build` directories; profile/image identities are checked and the build target is run again. Optional `transition_reports` must match the resulting executable hash and have passed without changed frames.

The output includes `REPORT.md`, a JSON matrix for every inventoried executable candidate, build/boot logs and separate compilation and execution counts. Missing revisions or fixtures fail the build gate. Unmapped candidates, discovery problems and indirect sites remain visible even when every mapped module compiles. Use `--require-complete` to fail on those static findings too; current profiles do not pass that stricter gate. A successful boot or a module appearing in execution coverage does not certify all its functions, all calling states or hardware fidelity. The Premium Disc needs its own verified revision profile and local input before it can enter this suite.

The source/synthetic GitHub workflow runs on pushes and pull requests using the pinned runtime and invented test data. It runs the Python suite and required runtime regressions without game assets. Real module compilation, visual comparisons and transition coverage remain local gates; CI success cannot stand in for unavailable gameplay fixtures. Packaged Linux/macOS validation also treats Python test failures as required failures.

Profiles can describe independently loaded images within `module_containers`. Scenario 3 v25.1 loads one of 69 0x8000-byte sections of `EFFECT.BIN` at 0x06048D00. The loader supplies the file ID, section offset and length; each section is a separate same-address overlay, not one large executable. Auditing and generation verify the complete source against the disc manifest, then check slice bounds and the required export veneers. Derived images stay in the external `modules` directory, leaving the extracted disc inventory intact. Tests cover distinct same-address images, first/last sections, altered source bytes outside the selected section, invalid exports, collisions and re-expansion of audited profiles.

Scenario 2 v24 loads its separate X3 effect files at 0x06049000. The normal Healing Drop route exercises X3ITEM; other effects with matching loader/export evidence are compilation candidates until exercised. X3ELEM5 remains under review because its exports do not fit that destination. X046 also has distinct revision-specific destinations in all three scenarios; loader evidence permits compilation but does not certify its gameplay path.

Scene (X1) modules also get entries for callbacks that only their own data tables point to (`tools/scene_data_entries.py`): an aligned word that points into the same image becomes an entry only when a straight walk from it decodes as plausible SH-2 code. `generate.py` logs every accepted and rejected candidate to `scene-data-entries.tsv` in the generated-code directory and prints a per-module count.

## Known coverage limits

Direct loader/call evidence now covers X025 at 0x06078000 in Scenarios 2/3, X048 at 0x06049000 in Scenario 2 or 0x06048D00 in Scenario 3, and X049 at 0x060A0000 in Scenarios 1/2 or 0x06048D00 in Scenario 3. These scene/ending paths remain unexecuted in the current route suite. Some scene programs first request files with r5=0, then load them to a real destination later; the earlier zero-destination request alone must not establish a mapping. Numeric file IDs also appear in unrelated resource APIs, so an equal integer is not loader evidence.

The normal/special X014 dispatch tables resolve 81, 93 and 111 entries respectively to mapped effect images across the three scenarios. Keep this static check distinct from actual effect execution. Validate configured seed alignment, complete-instruction bounds and non-wrapping load extents before auditing or generating code; synthetic tests cover both the flat-module and container paths.

Scenario 2's X1SAR_S2 still has discovery failures and an apparent layout inconsistency: its veneer at offset 0x3C targets 0x0605F060, while offset 0x60 contains a small return routine. This suggests a different layout may be involved, but neither a replacement address nor an unused-file classification is established. Keep this finding visible and obtain loader or execution evidence before changing its mapping.

The audited profile can emit far more scene programs than have been exercised. Review unresolved indirect targets, ambiguous overlays and load-address findings rather than treating compilation as execution proof. Current local nine-route validation covers 12 X1 scenes out of 169 compiled scene modules. The complete game, other scenarios/regions, translation patches and full hardware fidelity remain unvalidated.

The runtime patch must be reproducible against the exact commit in `dependencies.json`. Keep the upstream MIT notice with it. Generated game C++, object files and executables stay external even when they are useful for debugging. No public CI job should require or download copyrighted game or BIOS files.

## Presentation performance checks

Measure visible play separately from `SF3_GPU_OFFSCREEN`: the diagnostic path reads the GPU picture back every field and synchronizes work that visible play can overlap. Its fields-per-second result is not an on-screen FPS estimate. Report Saturn fields, distinct rendered pictures, audio underruns and the tested interval separately; a game can run at 60 fields/sec while changing its picture roughly 30 times/sec.

The AI renderer retains a bounded 64 MiB working set of recent replacement materials, reuses identical packed overlay inputs, and uses the native decoder's texture fingerprint only as a lookup hint. Dimensions and complete original pixel bytes still determine whether a replacement matches. Tests cover stale fingerprints, working-set limits, empty/populated transitions and sprites with different command types. Geometry uploads share a reusable cycling transfer buffer; queued-frame tests check growth and in-flight data isolation. `SF3_AI_GPU_CACHE_DISABLE=1` permits an external diagnostic comparison with overlay/residency reuse disabled. Native saves, scene execution and game timing are independent of these presentation caches.
